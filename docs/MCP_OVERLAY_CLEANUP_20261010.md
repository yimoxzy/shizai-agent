# 桌面红色遮罩残留：停止确认与误报修复

## 现场证据

用户报告停止操作后整个桌面仍有红色遮罩。本机安装元数据仍为
`0.7.31`，仓库发布基线为 `0.7.32`；本次修改尚未替换运行中的 MCP。

首次读取抖音流程 `c_Utpcsxeduw` 的调试状态为 `cleanup_timeout`，
`AppRunService.stop` 上次调用超时，`cleanup_complete=false`。再次调用正式
MCP `shizai_rpa_debug_stop` 后，运行状态变为 `stopped`，
`stop_acknowledged=true`，运行清理确认完成。

随后停止 DeepCapture，发现两个问题：

- `stopDeepCaptureInspect` 通道无响应，但旧实现仍返回并持久化
  `overlay_state=inactive`；外层 `stopDeepCapture` 的业务回执为成功时，
  又覆盖了拾取层停止失败的状态。
- `shizai_extension_stop_capture(project_ref="c_Utpcsxeduw")` 把应用 ID
  当成当前目录下的相对路径，回执出现
  `D:\agent\indeed_mcp\c_Utpcsxeduw`。流程真实目录位于设计器 applications 下。

Computer Use 截图显示实在 Agent 和 Chrome 目标窗口内容没有红层。
窗口内容截图不能独立证明其它进程的全桌面覆盖层已经消失。后续屏幕复核
被 Computer Use 自动检查中止，原因是无法可靠识别当前浏览器 URL；本轮停止
继续使用 Computer Use，没有把接口成功或窗口截图当成全桌面清理成功。

尝试通过现有 `NativeScreenshotCapture.stop` 清理另一种原生截图拾取层，
设计器返回 `40009995`（当前编辑入口不支持该动作）。此尝试未成功，
不能作为截图拾取层已停止的证据。

此前调试留下的临时 `pause-video-for-design` 节点已通过原生 MCP 的
revision 预览与提交删除，恢复原来的 8 步流程。没有重新运行评论采集。

## 通用修复

1. 拾取停止超时、拒绝或缺少成功确认时，返回 `unknown`、
   `cleanup_complete=false` 和重试提示，保留最后的拾取状态。
2. 外层采集会话停止不再覆盖拾取层清理失败。待清理标记跨进程持久化，
   不因旧会话过期而变成“遮罩已关闭”；重复停止成功后才清除标记。
3. 清理待确认时，自动恢复页面读取先要求完成停止，避免重新打开采集会话。
4. CLI/MCP 的停止入口统一解析应用 ID 到真实项目目录。
5. 小卡、接管框、运行遮罩均检查成功回执；遮罩的 renderer 关闭失败
   或未确认时返回未知可见状态，运行状态不会代替界面清理结果。
6. MCP 单独返回 `ui_cleanup_complete`。运行停止已完成但界面清理未确认时，
   顶层 UI 提示仍保留 `unknown`，不伪装为全部清理完成。
7. renderer 的显式错误优先于空结果处理；`result=null,error=null` 的正常
   void 回执仍可作为 RPC 确认。

这些改动不包含抖音、京东或具体页面选择器。

## 验证

针对性回归最终 **54 项通过**，其中新增的清理回归 20 项，覆盖拾取超时、
无确认、关闭拒绝、renderer 失败、跨进程重试、过期待清理状态、应用 ID
解析、项目目录已移除时的清理，以及既有进度卡生命周期。
Ruff、Python 编译与 `git diff --check` 通过。

完整回归发现原有“从已保存导航参数打开页面”测试缺少浏览器桥接的测试替身，
会访问当前已连接的真实扩展，并报 `tab_id_required`。已隔离桥接并重新验证
两个参数化用例，纳入上述 54 项通过结果。完整回归最终为 719 项通过、
上述 2 项旧测试失败，耗时 1038.84 秒；该进程在测试隔离修复前已加载旧测试。
真实安装目录的大型项目与组件扫描占用较长时间。失败用例已在修复后的
专项回归中通过，没有宣称修复后重新完整执行了全套测试。

另行复查 npm：本机 `npm view` 返回 `latest=0.7.29`，直接访问官方 registry
超时。因此前次发布 `0.7.32` 的 npm 可用性仍未确认，不能把“发布命令已执行”
当成 npm 用户已经可以下载新包。

用户随后通过现场确认明确回复“已经消失”。至此，本轮残留调试已停止，
桌面红色遮罩消失已获得用户确认，无需继续请求截图或启动新的拾取会话。

本次源码修复尚未打包、发布或进入当前已加载的 MCP 进程。
现场遮罩消失来自本轮停止与清理操作，不能当成新代码已部署的证据。

## 后续发布验证

在用户确认遮罩消失后，继续检查工具返回值，发现运行状态的精简呈现层
使用 `or` 合并清理字段，会丢失当前 `false`，甚至取到历史的 `true`。
已改为按字段是否存在选择当前值，并保留独立的 `ui_cleanup_complete`。
新增 5 项回归覆盖直接/嵌套响应和历史状态覆盖问题。

发布前专项回归及发布完整性测试合计 **73 项通过、389 项未选中**，
Ruff、Python 编译、`git diff --check` 与 npm 包内容预览通过。
版本号同步升级为 `0.7.33`。

再次访问官方 npm registry，附加缓存刷新参数后收到 HTTP 200，
确认 `0.7.32` 已存在，`latest=0.7.32`。此前普通 `npm view` 的
`0.7.29` 是旧元数据，不能据此判断发布失败；后续发布验收同时核对
官方仓库的具体版本与标签，不仅依赖旧缓存查询。

抖音流程复查仍为 8 步，调试状态为 `stopped`。独立浏览器扩展连接正常，
截图可直接观察当前视频页并按点定位元素，无需启动原生红色拾取层。
现有采集步骤仍为 JS，原生父子采集未完成；实时目录查询没有提供可直接
写入的通用嵌套循环结构，不能将多写两个线性采集节点等同于完整父子采集。
