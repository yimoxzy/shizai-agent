## 开发过程与修复

1. 阅读现有桥接实现，确认每个 MCP 进程都会独占同一端口，第二个进程只能返回 `bridge_in_use`。
2. 保留原扩展的连接协议。在同一回环端口增加 `/mcp`，本地调用方用安装密钥鉴权后转发请求。
   浏览器 Origin 即使带正确密钥也不允许接入该通道。密钥不会写入测试输出或状态结果。
3. 通过请求 ID 将结果返回原调用方。共享调用方退出只关闭自己的连接。
   持有者退出后，下一次调用重新尝试监听，或加入其它已接管的进程。
4. 扩展连接断开时，立即结束等待中的请求。点击/输入可能已生效，返回 `unknown`，不重放。
   在请求发送前失败则返回 `not_sent`；状态读取失败明确允许重试。
5. 修复原有等待逻辑：扩展在短暂等待后上线时，继续执行最初请求，不能只返回一个 `ready` 状态。
6. 调整引导：缺少配置才建议安装；已有监听但尚未连接时，提示打开浏览器、检查扩展与重连。
   旧版进程或不一致密钥占用端口时，明确提示更新/重启旧进程或核对配置。
7. 自检补充了发现与读取状态之间退出的竞态、发送瞬间断线/超时、过期响应隔离、
   2 MB 图片传输和真实双进程验收。

## 验收场景

| 场景 | 验收条件 |
| --- | --- |
| 两个 MCP 窗口 | 一方 owner，另一方 shared，均获得对应结果 |
| 两个窗口响应乱序 | tabId 不串线；requestId 唯一 |
| 关闭共享调用方 | 持有者和扩展仍然可用 |
| 关闭持有者 | 存活调用方接管端口，扩展重新连接后可继续读标签页 |
| 点击后断线 | 2 秒内返回 unknown；下次只发起明确的新请求 |
| 请求超时、迟到响应 | 不自动重放，也不污染后续请求 |
| 扩展晚于请求连接 | 执行原请求并返回其实际结果 |
| 错误密钥、网页 Origin、扩展 Origin | 全部拒绝 relay 访问 |
| 旧版占用端口 | 返回可操作恢复提示，不误报需要安装扩展 |
| 大图片和页面过期错误 | 2 MB 图片完整，页面过期错误保留 |
| stdio 关闭 | 两个实际 MCP 子进程的 stderr 均为空 |

## 边界与下一步

- 协议测试中的扩展是受控对端，不能据此声称京东采集或原生 RPA 运行成功。
- 本次不是常驻系统服务：所有 MCP 进程退出后，连接在下一次启动 MCP 时恢复。
- 共享桥接不提供页面独占租约。设计页和验证页仍应按 tabId 区分，页面变化后重新截图。
- 发版验收需检查实际 EXE 的版本、工具清单、浏览器连接、关闭 stderr 和安装包哈希。
  后续新增能力应进入新版本，并按既定 Gitee → GitHub/npm 顺序发布。
